# GRE Vocab Coach 安全與程式品質稽核報告

**日期**:2026-08-11 · **範圍**:全專案(92 個 TS/TSX 檔、10 個 SQL 檔、CI/設定檔)· **方法**:逐檔人工審閱 auth 層 → API routes → server actions → RLS/SQL → 資料層 → 前端元件 → 設定與 CI,輔以 npm audit 與 secrets 掃描。

## 總評

整體品質**明顯高於一般 side project**:RLS 政策完整、admin 允許清單 fail-closed、PostgREST filter injection 有集中防護(`src/lib/search.ts`)、1000-row 截斷有系統性解法(`fetchAllPages`)、錯誤訊息有統一遮罩(`src/lib/errors.ts`)、沒有 XSS sink、沒有 secrets 進版控、Next.js 15.5.18 已修補 CVE-2025-29927。以下發現多為中低嚴重度,依優先順序排列。

---

## 中優先(建議先修)

### M1. `/api/import` 未登入時回 307 redirect,前端會直接崩潰
- **位置**:`src/app/api/import/route.ts:19`、`src/components/CsvImportForm.tsx:19`
- **問題**:route handler 用 `requireUser()`,未登入(或 session 過期)時丟 `redirect("/login")` → fetch 會跟隨 redirect 拿到 login 頁 HTML,`response.json()` 直接 throw,是 unhandled rejection:`isSubmitting` 卡在 true、畫面沒有任何錯誤訊息。其他三個 API route 都是回 401 JSON,只有 import 不一致。
- **建議**:import route 改成和 dictionary/practice 一樣手動檢查 user 並回 `401` JSON;`CsvImportForm` 的 fetch 包 try/catch 並檢查 `response.ok`。

### M2. Import 把所有未追蹤單字立即排入複習,繞過漸進排程設計
- **位置**:`src/app/api/import/route.ts:122-128`
- **問題**:import 成功後為「所有」沒有 progress row 的單字建立 `next_review_at = now()` 的 row。這與 `initializeUserProgressAction`(`src/app/dashboard/actions.ts:41-50`)用 `staggeredDueDate` 分天滴灌的設計直接矛盾——`queue-plan.ts` 的註解明確說「一次全部 dated now 會淹沒排程、讓後續 interval 失去意義」。雖然每日上限(`planDailyQueue`)擋住了單日爆量,但 highest-frequency-first 的引入順序完全喪失(全部同時到期後,排序變成 `next_review_at asc` 而非頻率優先)。
- **建議**:import route 改用與 `initializeUserProgressAction` 相同的 `staggeredDueDate` 邏輯(或直接抽成共用函式呼叫)。

### M3. 「今天」的時區三套標準,dashboard 與 stats 對不上
- **位置**:`src/lib/data.ts:68-69`(UTC)、`src/lib/review-stats.ts:23`(硬編 `Asia/Taipei`)、`src/app/dashboard/actions.ts:39-40`(UTC)
- **問題**:dashboard 的 `reviewedTodayCount`/`completionPercent` 用伺服器時區的午夜(Vercel 上是 UTC,即使 region 設 hnd1),stats 頁的每日長條圖卻用台北時區分桶。台灣使用者早上 8 點前的複習,dashboard 會算成「昨天」,而 stats 圖算「今天」;dashboard 的「今日進度」在台北時間早上 8 點才歸零。`initializeUserProgressAction` 的 `startOfToday` 同樣是 UTC。
- **建議**:統一一個時區來源(短期:全部硬編 `Asia/Taipei` 與 review-stats 一致;長期:存進 user_settings)。

### M4. `submitReviewAction` 完全信任 client 輸入
- **位置**:`src/app/review/actions.ts:17-27`
- **問題**:`rating`、`reviewMode`、`responseTime`、`confidenceLevel` 只有 TypeScript 型別(runtime 無效),惡意 client 可送任意值。目前靠 DB 的 enum/check constraint 兜底,所以不是資料完整性漏洞,但:(1) 非法值變成 generic「Something went wrong」而非 400;(2) `reviewMode?.startsWith("practice_")` 決定 `recognitionOnly`,client 可謊報 `flashcard` 讓選擇題答對也走 2 倍 interval 快速「精通」(只影響自己的資料,但破壞 SRS 有效性);(3) `responseTime` 可送任意大整數污染自己的統計。
- **建議**:比照 `settings/actions.ts` 用 zod schema 驗證(rating/reviewMode 用 enum whitelist、responseTime 上限如 10 分鐘、confidenceLevel 1-5),失敗回明確錯誤。

## 低優先(排入 backlog)

### L1. CSV 匯出無公式注入(formula injection)防護
- **位置**:`src/app/api/export/route.ts:6-9`
- **問題**:`escapeCsv` 只處理引號,沒有中和以 `=` `+` `-` `@` 開頭的儲存格。若字庫內容含惡意字串,匯出檔在 Excel 開啟會執行公式。目前 vocabulary 只有 admin 能寫入,實際風險低,屬 defense-in-depth。
- **建議**:對以 `=+-@` 開頭的值前綴 `'` 或 tab。

### L2. 任何註冊帳號都能下載完整字庫
- **位置**:`src/app/api/export/route.ts:11-12`
- **問題**:註冊是開放的,任何人註冊即可 GET `/api/export` 匯出全部 2,060 字(含 Mason 書籍內容——`slide/` 都特意 gitignore 標注版權了)。與 import 限 admin 的謹慎程度不對稱。
- **建議**:若字庫內容有版權顧慮,export 也套 `isAdminUser` 或至少加 rate limit;若接受公開則明文註解此為刻意決定。

### L3. 相依套件 4 個 high 級別警告(皆為 transitive)
- **位置**:`package-lock.json`
- **問題**:`npm audit` 報 postcss(在 next 內)path traversal 與 sharp(libvips CVE)共 4 個 high,均有修復版。app 本身不處理使用者上傳圖片,實際暴露面小。
- **建議**:跑 `npm audit fix` 並在 CI 加 `npm audit --omit=dev --audit-level=high` 步驟。

### L4. 多處 fetch 缺少 `response.ok` 檢查與 try/catch
- **位置**:`src/components/CsvImportForm.tsx:15-19`、`src/components/practice/practice-shell.tsx:64-65`、`src/components/dictionary/dictionary-shell.tsx:46-51`
- **問題**:網路錯誤或非 JSON 回應會變 unhandled rejection,UI 卡在 loading 狀態。`blitz-game`/`match-game` 有做 try/catch,可比照。
- **建議**:統一包一個 `fetchJson` helper(檢查 `response.ok`、catch、回統一錯誤形狀)。

### L5. Import 無交易性 + 併發 TOCTOU
- **位置**:`src/app/api/import/route.ts:96-108`
- **問題**:(1) chunked insert 中途失敗時,前面 chunk 已寫入,回報 500 但實際部分匯入(重跑會被 dedup 吸收,可自癒,但回報數字誤導);(2) 「查現有 → insert」非原子,兩個 admin 同時匯入同字會撞 `vocabulary_word_pos_unique_idx` 變 500。單人使用機率極低。
- **建議**:insert 改 `upsert … onConflict: "normalized_word"` 式寫法,或用 Postgres function 包交易;至少在錯誤訊息註明「部分已匯入,重跑即可」。

### L6. `getTodayReviewQueue` 在頁面 render 中寫資料庫
- **位置**:`src/lib/data.ts:311-317`(由 `src/app/review/page.tsx` 呼叫)
- **問題**:開啟 /review 這個 GET render 會 upsert progress rows(副作用)。冪等 upsert 已處理併發,但 prefetch/爬蟲/重新整理都會觸發寫入,語意上 GET 應無副作用。
- **建議**:可接受現狀;若要改,把「引入新字」改為顯式按鈕或進 session 時的 action。

### L7. SRS 的「Hard」評分計為答錯
- **位置**:`src/lib/srs.ts:78-88`
- **問題**:rating=hard 會 `wrongCount + 1`,導致該字進入 Mistakes 清單、stats 準確率也算答錯。「想起來但吃力」與「答錯」語意不同;使用者可能困惑為何按 Hard 的字出現在錯題本。
- **建議**:若為刻意設計(把吃力字當弱點追蹤)請加註解;否則 hard 不加 wrong_count,或另設 `hard_count`。

### L8. vocab-cache 與 RLS 的隱性耦合
- **位置**:`src/lib/vocab-cache.ts:14-18`
- **問題**:module-level 快取用「當下請求的 cookie client」抓 vocabulary,結果跨使用者共享。現在 vocabulary 的 RLS 是全體 authenticated 可讀所以安全,但若未來改成 per-user 可見性,這裡會變成跨使用者資料洩漏點,而且很難察覺。
- **建議**:加上明確註解警告此前提;或改用 service-role client 抓(明示「這是全域共享資料」)。

### L9. 密碼強度僅靠 Supabase 預設(6 字元)
- **位置**:`src/components/AuthForm.tsx:51-54`
- **問題**:signup 無 client 端密碼強度檢查、無確認密碼欄位,placeholder 寫「At least 6 characters」但無驗證。開放註冊的公開站建議至少 8 字元 + Supabase 後台開啟 leaked-password protection。

### L10. 小型競態:match-game 最佳成績可能少計 1 秒
- **位置**:`src/components/game/match-game.tsx:151-157`
- **問題**:`finishRound` 讀 closure 中的 `seconds`,計時器 tick 與完成點擊競態時最佳紀錄可能差 1 秒。純顯示性,影響極小。

### L11. dictionary 兩段查詢可平行
- **位置**:`src/app/api/dictionary/route.ts:27-42`
- **問題**:exact match 與 suggestions 兩個查詢是串行 await,可 `Promise.all` 平行省一個 round trip(~50-100ms)。

## 已確認安全、無需修改的項目

| 檢查項 | 結果 |
|---|---|
| RLS 政策(4 張表 select/insert/update/delete) | ✅ 完整,皆 `auth.uid() = user_id`;vocabulary 寫入僅 service role |
| Admin 允許清單 | ✅ `ADMIN_USER_IDS` fail-closed,未設定即無人可 import |
| Service-role key 隔離 | ✅ 僅 `src/lib/supabase/admin.ts`,無 client component 引用 |
| PostgREST filter injection | ✅ `src/lib/search.ts` 集中 strip `,.()%*\"'`,含實測註解 |
| XSS | ✅ 無 dangerouslySetInnerHTML/innerHTML/eval,全靠 React escaping |
| 1000-row 截斷 | ✅ `fetchAllPages` 系統性分頁,關鍵讀取全數使用 |
| 錯誤訊息洩漏 | ✅ `errors.ts` 統一遮罩,DB 細節只進 server log |
| Secrets | ✅ `.env*` 全在 .gitignore,repo 無真實金鑰,CI 用 placeholder |
| Next.js 版本 | ✅ 15.5.18,CVE-2025-29927(middleware bypass)已修補;且授權檢查都在 server component/action 層,不依賴 middleware |
| Security headers | ✅ XFO/nosniff/Referrer-Policy/Permissions-Policy/HSTS(無 CSP 有註明原因) |
| CSRF | ✅ server actions 有 Next 內建 origin 檢查;route handlers 靠 SameSite=Lax cookie,跨站 POST 不帶 cookie |
| Upload DoS | ✅ import 有 2MB 上限,且在讀取前檢查 |
| DB 約束 | ✅ enum + check constraints 為 server 驗證缺口兜底 |
